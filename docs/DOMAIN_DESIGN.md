# Phase 4 – POS-Ready Product / Inventory / Order Domain Design

## Overview

This document explains the data model and design decisions for Phase 4: POS-aware product, menu, inventory, and order domain.

The primary goal is **not** a complete customer-facing order UI. Instead, this phase establishes a stable internal data model that can support:
- Normal orders
- Subscription orders
- Production recommendation
- POS menu synchronisation
- POS order push
- Sold-out / inventory status tracking

---

## 1. Product Domain

### `Product` (master catalogue)

The internal master record for every item sold.

| Field | Type | Notes |
|---|---|---|
| `id` | cuid | Primary key |
| `name` | String | Display name |
| `slug` | String (unique) | URL-safe identifier, e.g. `plain-bagel` |
| `description` | String? | Optional description |
| `category` | ProductCategory | BAGEL / SANDWICH / SPREAD / DRINK / OTHER |
| `basePrice` | Float | Base selling price before options |
| `isActive` | Boolean | Whether product is visible and orderable |
| `isSubscriptionEligible` | Boolean | Whether this can be included in a subscription box |
| `sortOrder` | Int | Display order in lists |
| `createdAt`, `updatedAt` | DateTime | Audit timestamps |

**Design principle:** Products are the internal master data. All POS-imported items are eventually mapped to an internal Product via `ExternalProductMap`.

### `ProductVariant`

Optional size / bundle / bread-choice variants. Currently minimal but extensible.

- Each variant has a `priceDelta` (positive or negative) relative to `basePrice`
- Designed to support future "size" or "bundle" selections

### `ProductOptionGroup` + `ProductOption`

Groups of selectable options attached to a product.

Examples:
- Group: "Bagel Choice" (minSelect=1, maxSelect=1, isRequired=true)
  - Plain Bagel (+$0), Sesame Bagel (+$0), Everything Bagel (+$0)
- Group: "Add-ons" (minSelect=0, maxSelect=3)
  - Add Bacon (+$2.50), Extra Cream Cheese (+$1.00), Add Avocado (+$2.00)

## 2. Why `DailyInventory` Instead of Traditional Stock

Traditional e-commerce uses perpetual inventory (quantity on hand decremented per sale). Bagels Beyond operates as a **bakery with daily production cycles**:

- Bagels are baked fresh each day in a planned quantity
- "Inventory" is per-product per-day, not a running total
- `isSoldOut` can be set immediately regardless of `soldQty`
- `plannedQty` is set the night before based on prediction recommendations
- `bakedQty` is updated when production is complete
- `soldQty` will eventually be populated by POS aggregation or internal order data

| Field | Notes |
|---|---|
| `plannedQty` | How many are planned to bake (set from prediction) |
| `bakedQty` | How many were actually baked |
| `reservedQty` | Reserved by subscription or confirmed orders (future auto-calculation) |
| `soldQty` | How many have been sold (future: auto-calculated from POS/orders) |
| `isSoldOut` | Override flag — can be set manually at any time |
| `note` | Free text for staff notes |

**Unique constraint:** `(productId, date)` — prevents duplicate inventory entries.

### Connection to `DailyRecord`

`DailyInventory` and `DailyRecord` are currently **loosely coupled** — both have a `date` field that can be joined. Strong coupling is intentionally avoided in this phase. Future production recommendation logic will be able to:

1. Read `SalesPrediction.recommendedBagelsToBake` for a date
2. Check confirmed `Order` counts for that date
3. Check subscription quantities for that date
4. Sum all three into `DailyInventory.plannedQty`

## 3. Order Domain

### `Order`

Shared structure for all order types.

| Field | Notes |
|---|---|
| `orderNumber` | Human-readable unique identifier, e.g. `ORD-20260325-00042` |
| `userId` | Nullable — supports guest checkout in future |
| `status` | DRAFT → PENDING → CONFIRMED → PREPARING → READY → COMPLETED / CANCELLED |
| `paymentStatus` | UNPAID / PAID / REFUNDED / PARTIALLY_REFUNDED |
| `fulfillmentType` | PICKUP / DELIVERY / DINE_IN |
| `source` | INTERNAL / SUBSCRIPTION / POS_IMPORTED |
| `customerXSnapshot` | Name/email/phone at order time — preserved even if profile changes |
| `subtotalAmount`, `discountAmount`, `totalAmount` | Pre-calculated amounts |

### `OrderItem` + `OrderItemOption`

**Snapshot pattern:** At order creation, all product names and prices are copied into `productNameSnapshot`, `unitPriceSnapshot`, and `priceDeltaSnapshot`. This means:

- If a product's name or price changes later, historical orders are **unaffected**
- POS-imported orders can reference products that may not exist in the internal catalogue (via nullable `productId`)

### Order Sources

```
INTERNAL      → created via internal admin or customer UI
SUBSCRIPTION  → generated by subscription renewal logic (future)
POS_IMPORTED  → imported from Loyverse or another POS (future)
```

All three share the same `Order` model. The `source` field distinguishes them.

## 4. POS Integration Architecture

### `ExternalProductMap`

Links an internal `Product` to an external POS product ID.

```
Product  ←──  ExternalProductMap  ──→  Loyverse Item
(internal)         (bridge)            (external)
```

During catalogue sync:
1. Fetch all items from Loyverse via `LoyverseAdapter.fetchExternalCatalog()`
2. For each item, look up `ExternalProductMap` by `(source, externalProductId)`
3. If mapping exists → update the linked internal Product
4. If mapping doesn't exist → create a new Product + mapping

### `ExternalOrderMap`

Tracks the sync status of pushing an internal Order to the POS.

```
Order  ←──  ExternalOrderMap  ──→  Loyverse Receipt
```

`syncStatus` values: `pending` / `synced` / `failed`

### Adapter Pattern

Located in `lib/integrations/adapters/pos/`:

```
types.ts        — POSAdapter interface + shared types
loyverse.ts     — Loyverse implementation (placeholder, ready for API key)
```

To add Square or another POS, create `square.ts` implementing the same `POSAdapter` interface.

Services in `lib/integrations/services/`:
- `catalog-sync.ts` — `syncExternalCatalog(adapter, source)`
- `order-sync.ts`   — `pushOrderToPOS(orderId, adapter, source)`

## 5. Future Connection Points

### Production Recommendation
`SalesPrediction.recommendedBagelsToBake` + confirmed order quantities + subscription quantities → `DailyInventory.plannedQty`

### Subscription Orders
Set `Order.source = SUBSCRIPTION`, link to customer subscription record (future model). `DailyInventory.reservedQty` will be populated from active subscriptions.

### POS Sold Quantity Sync
After running `syncInventoryFromExternal()`:
- Get sold quantities per `externalProductId` from Loyverse receipts
- Look up `ExternalProductMap` to find internal `productId`
- Upsert `DailyInventory.soldQty`

## 6. Not Yet Implemented

The following items are **intentionally deferred** to future phases:

| Feature | Status |
|---|---|
| Real Loyverse API calls | Placeholder only — needs `LOYVERSE_API_KEY` env var |
| Customer-facing order UI | Architecture ready, UI not built |
| Payment processing (Stripe etc.) | `paymentStatus` field exists, no gateway connected |
| Subscription renewal engine | `isSubscriptionEligible` flag exists, no scheduler |
| POS menu webhook sync | Manual catalogue sync only |
| Order status email notifications | Not implemented |
| Guest checkout (non-user orders) | `userId` is nullable, no UI |

## 7. Admin Pages Added

| Path | Purpose |
|---|---|
| `/admin/products` | List all products |
| `/admin/products/new` | Create a new product |
| `/admin/products/[id]` | Edit an existing product |
| `/admin/inventory` | Daily inventory management |

All routes require `ADMIN` role, enforced server-side via `requireAdmin()` on page loads and `apiRequireAdmin()` on API routes.
